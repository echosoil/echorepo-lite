# ECHOREPO Data API and Canonical Data Guide

**Audience:** external data users, data providers, integrators, validators, and researchers who need to retrieve ECHOREPO data programmatically and verify the canonical CSV resources.

**Current implementation basis:** `echosoil/echorepo-lite`, `main` branch, reviewed against the implementation on **2026-08-07** (latest `main` commit observed while preparing this guide: `92a864b7294e2fd339dfcb53184c37a02e747dc4`).

**Production API base used by the ECHOREPO publication workflow:**

```text
https://echorepo.quanta-labs.com/api/v1
```

**Canonical Zenodo concept DOI:**

```text
https://doi.org/10.5281/zenodo.19722513
```

> **Recommended external workflow:** use `GET /api/v1/canonical/all.zip`, authenticate with `X-API-Key` or a Bearer token, extract `samples.csv`, and validate it against the public canonical schema described below. The machine bundle is the clearest public data contract in the current code.

---

## 1. What is the canonical export?

ECHOREPO stores data internally in PostgreSQL, but the public machine-readable export intentionally uses a stable, user-facing schema. Some database field names are renamed in the canonical CSV files, timestamps are normalized to UTC/ISO 8601, soil texture and structure are standardized, and repeated laboratory metadata are normalized into reference tables.

The machine-readable canonical bundle contains six CSV files:

```text
canonical_all.zip
├── samples.csv
├── sample_images.csv
├── sample_parameters.csv
├── sample_biodiversity.csv
├── parameter_definitions.csv
└── analysis_methods.csv
```

The API machine bundle contains **no leading comment lines**. The first line of each file is the CSV header.

When the same six CSV resources are published on Zenodo, the publication workflow also generates:

```text
file.json
```

`file.json` is CSVW-style machine-readable metadata describing the tables, columns, datatypes, checksums, primary keys, foreign keys, dataset-level metadata and the reserved/published DOI. It is generated by the publication workflow and is **not** part of `/api/v1/canonical/all.zip`.

## 2. Quick start

Set your API key without placing it directly in command history:

```bash
export ECHOREPO_API_KEY='YOUR_KEY'
export ECHOREPO_API='https://echorepo.quanta-labs.com/api/v1'
```

Check service availability:

```bash
curl -fsS "$ECHOREPO_API/ping"
```

Expected response:

```json
{"ok": true}
```

Download the complete machine-readable canonical bundle:

```bash
curl -fL \
  -H "X-API-Key: $ECHOREPO_API_KEY" \
  "$ECHOREPO_API/canonical/all.zip" \
  -o canonical_all.zip
```

Inspect it:

```bash
unzip -l canonical_all.zip
```

Extract only `samples.csv`:

```bash
unzip -p canonical_all.zip samples.csv > samples.csv
```

Validate the complete bundle with the companion validator:

```bash
python validate_echorepo_bundle.py canonical_all.zip
```

## 3. Authentication

The API authentication helper accepts several modes.

### Recommended: API key header

```http
X-API-Key: YOUR_KEY
```

Example:

```bash
curl -H "X-API-Key: $ECHOREPO_API_KEY" \
  "$ECHOREPO_API/canonical/all.zip" \
  -o canonical_all.zip
```

### Bearer token

OIDC/Keycloak JWTs can be supplied as:

```http
Authorization: Bearer YOUR_JWT
```

The server validates issuer/JWKS information and, when configured, audience/client identity.

### Compatibility API-key forms

The code also accepts:

```http
Authorization: ApiKey YOUR_KEY
```

and:

```text
?api_key=YOUR_KEY
```

The query-parameter form is supported for compatibility but is not recommended because URLs are more likely to be retained in logs, history, proxies and analytics.

### Session authentication

A logged-in ECHOREPO web session can satisfy API authentication for browser-originated requests.

### Authentication failure

A missing or invalid credential produces HTTP `401` and the API authentication helper returns:

```json
{
  "ok": false,
  "error": "Missing or invalid credentials"
}
```

## 4. API endpoint overview

### 4.1 Health

| Method | Endpoint | Authentication | Purpose |
|---|---|---:|---|
| `GET` | `/api/v1/ping` | No | Lightweight service health check. |

### 4.2 Recommended canonical machine export

| Method | Endpoint | Authentication | Purpose |
|---|---|---:|---|
| `GET` | `/api/v1/canonical/all.zip` | Yes | Preferred machine-readable canonical bundle; six clean CSV files. |
| `GET` | `/api/v1/canonical/zenodo_bundle.zip` | Yes | Deprecated compatibility alias for the same machine-bundle builder. |

`/canonical/all.zip` is the endpoint used by the current Zenodo publication tool.

The endpoint accepts the canonical sample filters described in section 5. Filters first identify matching `sample_id` values in `samples`, then all child resources are exported for those samples. The two reference tables remain complete so that the parameter data remain self-describing.

### 4.3 Canonical query endpoints

| Method | Endpoint | Formats / response | Main filters |
|---|---|---|---|
| `GET` | `/api/v1/canonical/samples` | JSON, CSV, GeoJSON | `from`, `to`, `country`, `bbox`, `within`, `fields`, `limit`, `offset`, `order`, `dir` |
| `GET` | `/api/v1/canonical/samples/count` | JSON count | `from`, `to`, `country`, `bbox`, `within` |
| `GET` | `/api/v1/canonical/sample_images` | JSON, CSV | `sample_id`, `country`, `from`, `to`, `fields`, `limit`, `offset` |
| `GET` | `/api/v1/canonical/sample_parameters` | JSON, CSV | `sample_id`, `country`, `parameter_code`, `fields`, `limit`, `offset` |
| `GET` | `/api/v1/canonical/sample_biodiversity` | JSON, CSV | `sample_id`, `country`, `marker`, `taxonomic_level`/`level`, `taxon`, `fields`, `limit`, `offset` |
| `GET` | `/api/v1/canonical/map.geojson` | GeoJSON | sample/time/country/spatial filters; map-specific paging |
| `GET` | `/api/v1/canonical/map.count` | JSON count | country/date/pH/QA filters |

For JSON responses, the tabular endpoints return a structure of the form:

```json
{
  "meta": {
    "count": 123,
    "limit": 100,
    "offset": 0
  },
  "data": [
    {}
  ]
}
```

The standard maximum page size for non-map JSON queries is `1000`. The map API uses a default of `2000` and a maximum of `10000`.

### 4.4 Operator endpoint

```http
GET /api/v1/canonical/snapshot/all.zip
```

This endpoint creates an unfiltered canonical machine snapshot and persists it to configured object storage. It is an operator/publication function rather than the normal external download route.

### 4.5 Legacy compatibility endpoints

```text
GET /api/v1/samples
GET /api/v1/samples/count
```

These use the legacy SQLite-oriented schema and are retained for backward compatibility. New integrations should prefer the canonical bundle.

### 4.6 Write endpoint

```text
POST /api/v1/lab-enrichment
```

This is an authenticated laboratory-ingestion endpoint, not part of the normal external read/download workflow.

## 5. Filtering the machine bundle

`GET /api/v1/canonical/all.zip` supports these filters.

### Date/time

```text
from=YYYY-MM-DD
to=YYYY-MM-DD
```

or ISO-8601 date-times.

Examples:

```bash
curl -fL \
  -H "X-API-Key: $ECHOREPO_API_KEY" \
  "$ECHOREPO_API/canonical/all.zip?from=2026-01-01&to=2026-06-30" \
  -o echorepo_2026_h1.zip
```

A date-only `to` value is implemented as an exclusive bound at the start of the following day, so the specified calendar day is effectively included.

### Country

Either spelling is accepted:

```text
country=ES
country_code=ES
```

Example:

```bash
curl -fL \
  -H "X-API-Key: $ECHOREPO_API_KEY" \
  "$ECHOREPO_API/canonical/all.zip?country=ES" \
  -o echorepo_es.zip
```

### Bounding box

```text
bbox=west,south,east,north
```

Example:

```text
bbox=-10,35,5,45
```

Longitude must be within `[-180, 180]`, latitude within `[-90, 90]`, and minimum values must not exceed maximum values.

### `within`

```text
within=lat,lon,radius_km
```

Important: in the current implementation this is a **latitude/longitude bounding-box approximation** around the requested centre, not an exact geodesic/radial distance calculation. It is suitable as a coarse spatial pre-filter but should not be interpreted as an exact circular query.

### Combined filters

Filters are combined with logical `AND`.

```bash
curl -fL \
  -H "X-API-Key: $ECHOREPO_API_KEY" \
  "$ECHOREPO_API/canonical/all.zip?country=ES&from=2026-01-01&bbox=-10,35,5,45" \
  -o echorepo_subset.zip
```

## 6. Public canonical data model

The relational structure is:

```text
samples.csv
  PK: sample_id
  │
  ├──< sample_images.csv
  │      PK: (sample_id, image_id)
  │      FK: sample_id -> samples.sample_id
  │
  ├──< sample_parameters.csv
  │      FK: sample_id      -> samples.sample_id
  │      FK: parameter_code -> parameter_definitions.parameter_code
  │      FK: method_code    -> analysis_methods.method_code
  │
  └──< sample_biodiversity.csv
         FK: sample_id -> samples.sample_id

analysis_methods.csv
  PK: method_code
  ▲
  │
parameter_definitions.csv
  PK: parameter_code
  FK: method_code -> analysis_methods.method_code
```

A child table is allowed to contain data for only some samples. The integrity rule is the opposite direction: **every child `sample_id` must exist in `samples.csv`**.

# 7. `samples.csv`: authoritative public schema

The public `samples.csv` currently has exactly these 26 columns, in this order:

```text
sample_id
sampling_datetime_utc
lat
lon
country_code
coordinate_obfuscation_radius_m
soil_ph_field
soil_organic_matter_estimate_pct
earthworms_count
contamination_debris
contamination_plastic
contamination_other_orig
contamination_other_en
pollutants_count
soil_structure_orig
soil_structure_en
soil_texture_orig
soil_texture_en
observations_orig
observations_en
metals_info_orig
metals_info_en
collected_by
data_source
qa_status
licence
```

## 7.1 Column dictionary

| Column | Type | Meaning / validation guidance |
|---|---|---|
| `sample_id` | string | Unique ECHOREPO sample identifier. Public primary key; required and unique. |
| `sampling_datetime_utc` | datetime | Sampling event date/time normalized to UTC ISO 8601. Blank is possible if the source timestamp cannot be normalized. |
| `lat` | number | Published latitude in WGS 84 / EPSG:4326. Validate `-90 <= lat <= 90`. |
| `lon` | number | Published longitude in WGS 84 / EPSG:4326. Validate `-180 <= lon <= 180`. |
| `country_code` | string | Country associated with the published location, normally ISO 3166-1 alpha-2 uppercase. |
| `coordinate_obfuscation_radius_m` | number | Radius in metres used to obfuscate the published coordinates for privacy. Published coordinates are not necessarily the exact sampling point. |
| `soil_ph_field` | number | Field-estimated soil pH from the ECHO simplified paper-strip workflow. It is not a laboratory pH result. |
| `soil_organic_matter_estimate_pct` | number | Field estimate of soil organic matter (SOM), based on visual comparison with the ECHO soil-colour chart. It must not be interpreted as laboratory-measured soil organic carbon. |
| `earthworms_count` | integer | Number of earthworms found manually in the sampled soil. |
| `contamination_debris` | number | Field derived from the visible-debris observation workflow. Exact encoding remains marked provisional in canonical metadata. |
| `contamination_plastic` | number | Field derived from the visible-plastic observation workflow. Exact encoding remains marked provisional in canonical metadata. |
| `contamination_other_orig` | string | Participant free-text information on other visible contamination / possible sources, original language. |
| `contamination_other_en` | string | English representation/translation of `contamination_other_orig`. |
| `pollutants_count` | integer | Count associated with the visible-pollutant workflow. Precise semantics remain marked provisional in metadata. |
| `soil_structure_orig` | string | Participant-recorded soil-structure class, original submitted language. |
| `soil_structure_en` | string | Canonical lowercase English soil-structure value derived from `soil_structure_orig`. |
| `soil_texture_orig` | string | Participant-recorded soil-texture class, original submitted language. |
| `soil_texture_en` | string | Canonical lowercase English soil-texture value derived from `soil_texture_orig`. |
| `observations_orig` | string | Additional participant observations in the original language. |
| `observations_en` | string | English representation/translation of the additional observations. |
| `metals_info_orig` | string | Participant-provided contextual/free-text information concerning metals, original language. |
| `metals_info_en` | string | English representation/translation of metals-related contextual information. |
| `collected_by` | string | Internal/pseudonymous collector identifier. Metadata currently marks this field provisional from a privacy/publication-policy perspective; consumers should not treat it as a durable person identifier. |
| `data_source` | string | Source system/workflow from which the canonical row was derived. |
| `qa_status` | string | ECHOREPO QA status for the canonical sample. Treat values as ECHOREPO-controlled status text rather than a universal vocabulary unless separately documented. |
| `licence` | string | Row/source licence statement. |

## 7.2 Coordinates are deliberately obfuscated

The dataset-level CRS is:

```text
WGS 84 (EPSG:4326)
```

The sampling protocol metadata describes discrete `0-30 cm` soil sampling. However, the published `lat` and `lon` represent an obfuscated location where an obfuscation radius is recorded. A consumer must therefore not infer sub-radius positional accuracy from the decimal precision of the coordinates.

## 7.3 Soil texture values

When `soil_texture_orig` maps successfully, `soil_texture_en` is one of:

```text
sandy
sandy loam
sandy clay
silty
silty clay
clayey
clay loam
other
no data
```

The original value is preserved in `soil_texture_orig`. If a submitted value has no mapping, the canonical English field can be blank.

## 7.4 Soil structure values

When `soil_structure_orig` maps successfully, `soil_structure_en` is one of:

```text
friable
intact
firm
compact
high compact
no data
```

Again, the original value is retained separately.

## 7.5 Public aliases versus PostgreSQL names

The database schema is intentionally not renamed. The public machine export applies these aliases:

| PostgreSQL/internal name | Public `samples.csv` name |
|---|---|
| `timestamp_utc` | `sampling_datetime_utc` |
| `location_accuracy_m` | `coordinate_obfuscation_radius_m` |
| `ph` | `soil_ph_field` |
| `organic_carbon_pct` | `soil_organic_matter_estimate_pct` |

The last alias is especially important: despite the historical internal name `organic_carbon_pct`, the public value is documented as a **field-estimated soil organic matter percentage**, not laboratory SOC.

# 8. Other canonical files

## 8.1 `sample_images.csv`

Columns:

```text
sample_id
country_code
image_id
image_url
image_description_orig
image_description_en
collected_by
image_datetime_utc
licence
```

Key rules:

```text
Primary key: (sample_id, image_id)
Foreign key: sample_id -> samples.csv:sample_id
```

`image_description_orig` preserves participant-provided image captions/explanations in the submitted language. `image_description_en` contains the English representation/translation where available.

Localhost image URLs can be rewritten to the configured public ECHOREPO base URL before export.

## 8.2 `sample_parameters.csv`

Columns:

```text
sample_id
country_code
parameter_code
result_value
unit
method_code
analysis_datetime_utc
lab_id
licence
```

This is a compact long-form measurement table. Human-readable parameter names, semantic URIs and method descriptions are deliberately not repeated in each measurement row.

Current canonical transformation rules include:

- oxide-form rows are excluded by default;
- numeric values strictly below `0.01` are omitted by default;
- a blank row unit can be filled from the parameter definition's `default_unit`;
- each exported `parameter_code` must exist in `parameter_definitions.csv`;
- each exported `method_code` must exist in `analysis_methods.csv`.

The current parameter dictionary contains elemental codes such as:

```text
As, Pb, Ca, Cd, Co, Cr, Cu, Fe, K, Mg, Mn, Mo, Ni, P, S, Zn
```

The default unit in the current curated definitions is `mg/kg`.

## 8.3 `parameter_definitions.csv`

Columns:

```text
parameter_code
parameter_name
parameter_uri
default_unit
method_code
parameter_description
```

Primary key:

```text
parameter_code
```

Foreign key:

```text
method_code -> analysis_methods.csv:method_code
```

`parameter_uri` may be blank where no reviewed vocabulary mapping has yet been approved. A blank URI is preferable to an invented/unverified URI.

## 8.4 `analysis_methods.csv`

Columns:

```text
method_code
method_name
method_description
procedure_uri
```

Primary key:

```text
method_code
```

The currently configured method is:

```text
method_code: MXRF_105C
method_name: Micro-X-ray fluorescence (µXRF)
method_description: Soil oven-dried at 105 °C to constant weight before total elemental concentration analysis.
```

`procedure_uri` may be blank pending a reviewed mapping.

## 8.5 `sample_biodiversity.csv`

Columns:

```text
sample_id
country_code
marker
taxon_rank
scientific_name
read_count
relative_abundance_pct
ingested_datetime_utc
source_file
licence
```

This is a compact taxonomic-abundance export, not raw OTU data.

Important semantics:

- `read_count` is a sequencing-read count, not a count of organisms;
- `relative_abundance_pct` is the reported relative abundance for the sample/marker/rank aggregation;
- `ingested_datetime_utc` is the time the result row was uploaded/ingested into ECHOREPO, **not** necessarily the laboratory analysis date;
- biodiversity rows are inner-joined to `samples`, preventing exported orphan `sample_id` values.

# 9. CSV formatting and timestamp behavior

The machine bundle is generated with pandas CSV output:

- UTF-8 text;
- comma delimiter;
- one header row;
- no index column;
- no ECHOREPO comment preamble in `/api/v1/canonical/all.zip`.

Timestamp fields in the public machine export are normalized to strings of the form:

```text
2026-08-06T14:11:44.689121Z
```

The relevant public timestamp columns are:

```text
sampling_datetime_utc
image_datetime_utc
analysis_datetime_utc
ingested_datetime_utc
```

Invalid/unparseable timestamp source values are converted to blank CSV cells rather than emitted in an inconsistent date-time format.

# 10. Validation workflow

## 10.1 Validate the archive structure

```bash
unzip -l canonical_all.zip
```

For the unfiltered canonical bundle you should expect the six CSV names listed in section 1.

```bash
    "soil_structure_en",
    "soil_texture_orig",
    "soil_texture_en",
    "observations_orig",
    "observations_en",
    "metals_info_orig",
    "metals_info_en",
    "collected_by",
    "data_source",
    "qa_status",
    "licence",
]

with zipfile.ZipFile("canonical_all.zip") as z:
    with z.open("samples.csv") as raw:
        import io
        r = csv.reader(io.TextIOWrapper(raw, encoding="utf-8-sig"))
        actual = next(r)

print("OK" if actual == expected else "HEADER MISMATCH")
print(actual)

```

## 10.3 Full validator

A companion script is supplied with this guide:

```text
validate_echorepo_bundle.py
```

Run:

```bash
python validate_echorepo_bundle.py canonical_all.zip
```

It checks:

- exact canonical headers and column order;
- required/unique `sample_id`;
- primary-key uniqueness where defined;
- numeric and integer parsability;
- UTC timestamp shape;
- latitude/longitude ranges;
- non-negative coordinate-obfuscation radius;
- canonical soil texture and structure vocabularies;
- sample foreign keys from images, parameters and biodiversity;
- parameter-code and method-code references;
- selected domain sanity checks such as pH and SOM ranges.

The pH `0..14` and SOM `0..100` tests are emitted as **warnings**, not hard schema errors, because they are useful consumer sanity checks but are not the same thing as constraints enforced by the current export code.

# 11. Browser downloads versus API machine downloads

ECHOREPO also exposes logged-in web routes such as:

```text
/download/canonical/samples.csv
/download/canonical/sample_images.csv
/download/canonical/sample_parameters.csv
/download/canonical/sample_biodiversity.csv
/download/canonical/all.zip
```

These are intended primarily for human-facing download workflows.

The individual browser CSV downloads add ECHOREPO metadata as leading lines beginning with `#`, for example a generated-at timestamp, description and snapshot information. This is useful to a human reader but can confuse generic CSV readers unless comment lines are explicitly skipped.

The API machine bundle:

```text
/api/v1/canonical/all.zip
```

does **not** add those comment lines and is therefore the preferred integration endpoint.

The browser `/download/canonical/all.zip` route also creates/persists a snapshot in configured object storage. The API machine bundle is generated for the request and returned directly.

# 12. Zenodo package and `file.json`

The ECHOREPO Zenodo workflow downloads `/api/v1/canonical/all.zip`, validates the public schemas, and publishes the six CSV files separately under a Zenodo dataset version. It also generates `file.json`.

A Zenodo version therefore has the logical structure:

```text
samples.csv
sample_images.csv
sample_parameters.csv
sample_biodiversity.csv
parameter_definitions.csv
analysis_methods.csv
file.json
```

`file.json` describes:

- each CSV resource;
- exact header order;
- column title, description and datatype;
- reviewed `propertyUrl` mappings where available;
- file byte size and SHA-256 checksum;
- primary keys;
- foreign keys;
- CSV dialect;
- dataset language;
- coordinate reference system;
- sampling depth and sampling method;
- licence, source, creators and DOI.

The current publication code validates that the columns in `file.json` exactly match each CSV header before publication.

### Primary keys encoded in CSVW

```text
samples.csv:                 sample_id
sample_images.csv:           (sample_id, image_id)
parameter_definitions.csv:   parameter_code
analysis_methods.csv:        method_code
```

### Foreign keys encoded in CSVW

```text
sample_images.sample_id
  -> samples.sample_id

sample_parameters.sample_id
  -> samples.sample_id

sample_parameters.parameter_code
  -> parameter_definitions.parameter_code

sample_parameters.method_code
  -> analysis_methods.method_code

sample_biodiversity.sample_id
  -> samples.sample_id

parameter_definitions.method_code
  -> analysis_methods.method_code
```

# 13. Current implementation compatibility notes

These notes describe the current code rather than an idealized future API.

### The machine ZIP is the authoritative public file schema

The exporter used by `/api/v1/canonical/all.zip` explicitly applies the public aliases and normalized schemas described in this document.

Some individual `/api/v1/canonical/...` query routes still use database-facing compatibility constants. In particular, the query API and the published machine CSV should not be assumed to have identical field naming until those routes are fully aligned with the public exporter.

For an external consumer that needs to validate the current published `samples.csv`, use:

```text
GET /api/v1/canonical/all.zip
```

rather than inferring the CSV contract from the direct query route.

### Reference tables are part of the data contract

`parameter_definitions.csv` and `analysis_methods.csv` are not optional explanatory extras. They are part of the normalized relational model and should accompany `sample_parameters.csv`.

### Empty semantic URIs are intentional

Where the project has not reviewed and approved an exact semantic URI, the corresponding URI cell can be blank. Consumers should not infer a missing URI from the parameter label alone.

### Child-table sparsity is normal

A sample does not need to have an image, laboratory measurement or biodiversity result. Therefore a child table can contain fewer distinct sample IDs than `samples.csv`.

The invalid case is an orphan child row whose `sample_id` is not present in `samples.csv`.

# 14. Suggested external consumer pattern

A robust integration can follow this sequence:

```text
1. GET /api/v1/ping
2. GET /api/v1/canonical/all.zip with authenticated request
3. verify HTTP success and ZIP integrity
4. verify the six expected CSV resource names
5. validate samples.csv header and sample_id uniqueness
6. validate datatypes/ranges
7. validate child -> parent sample_id foreign keys
8. validate parameter_code and method_code references
9. retain the downloaded archive or record its checksum/date for reproducibility
10. for a stable citable version, use the corresponding Zenodo version/concept DOI
```

For automated pipelines, fail on structural/schema/foreign-key errors and treat domain plausibility checks separately as warnings unless your downstream application has stricter requirements.

```bash
curl -fL \
  -H "X-API-Key: $ECHOREPO_API_KEY" \
  "https://echorepo.quanta-labs.com/api/v1/canonical/all.zip?country=ES" \
  -o canonical_es.zip
```

### Date range

```bash
curl -fL \
  -H "X-API-Key: $ECHOREPO_API_KEY" \
  "https://echorepo.quanta-labs.com/api/v1/canonical/all.zip?from=2026-01-01&to=2026-06-30" \
  -o canonical_2026_h1.zip
```

### Bounding box

```bash
curl -fL \
  -H "X-API-Key: $ECHOREPO_API_KEY" \
  "https://echorepo.quanta-labs.com/api/v1/canonical/all.zip?bbox=-10,35,5,45" \
  -o canonical_bbox.zip
```

### Bearer token

```bash
curl -fL \
  -H "Authorization: Bearer $TOKEN" \
  "https://echorepo.quanta-labs.com/api/v1/canonical/all.zip" \
  -o canonical_all.zip
```

## Appendix B — Python download example

```python
from pathlib import Path
import requests

API = "https://echorepo.quanta-labs.com/api/v1"
API_KEY = "YOUR_KEY"

response = requests.get(
    f"{API}/canonical/all.zip",
    headers={"X-API-Key": API_KEY},
    timeout=300,
)
response.raise_for_status()

Path("canonical_all.zip").write_bytes(response.content)
print("Downloaded", len(response.content), "bytes")
```

For production code, load credentials from environment variables or a secrets manager rather than hard-coding them.
